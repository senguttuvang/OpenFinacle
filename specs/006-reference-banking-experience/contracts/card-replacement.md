# Synthetic debit-card replacement and activation

Evidence date: 17 October 2026. Execution: `of-9hc.14`. Public [debit-card FAQs](https://www.icici.bank.in/personal-banking/cards/debit-card/debit-cards-faqs) document replacement through digital/branch channels and PIN-based activation. The public [reissue page](https://www.icici.bank.in/personal-banking/cards/debit-card/re-issue-of-lost-atm) documents blocking the existing card on new issuance and delivery to the recorded address. Its charges/timing and mixed retail/corporate material are not adopted as current product terms. No authenticated form, courier integration, internal staff page or PIN API was observed.

## Explicit simulation and persistent identity

Provide replacement for damaged/expired/lost synthetic debit instruments only. A new request captures an owned source card, version, reason and the customer's invented address confirmation. Lost cards must first use the existing immediate protective block; requesting replacement never implies an instant protective block. No actual PAN, PIN, CVV, OTP, fee, bank address change, courier or network instruction is collected or generated. The displayed replacement label is an opaque demo reference, not a credential. The existing generic replacement service case stays a request-only record and is not retroactively replayed into issuance.

Replacement creates a **distinct durable card**. The source instrument is permanently blocked on authorized issuance if it was not already blocked. Its row and history remain inspectable and cannot resume. Its historical controls are not silently copied to the new instrument. The replacement begins held with all channels disabled and a demo daily limit of ₹25,000. Independent issuance, simulated dispatch/delivery and customer activation are separate saved steps. No automatic delivery, elapsed-time completion, provisioning on read, or reset occurs.

D1 remains the explicit synthetic product owner. Fineract savings and postings stay unchanged. Existing `synthetic_cards` and `card_events` preserve the original instrument/immutable history. Add replacement request/event and replacement-card/event tables; adapt owned card enquiry/control services to both product stores through fixed internal repository selections. Do not relax legacy blocked-card guards or erase original records to overcome the one-original-card-per-relationship constraint. No new cloud resource, dependency, core fallback or financial ledger.

## States and authority

Customer reviews/edits and submits reason/address/source card. Officer may recommend or reject a submitted request; customer may cancel before recommendation. Separate approver may issue or reject a recommendation. Issuance atomically blocks the source if necessary, creates the held replacement once, links both instruments/request and appends product/case/audit histories. A source already replaced cannot be replaced again; a later request must reference the new instrument. Competing requests/issuances cannot create two successors for one source.

Officer explicitly records simulated dispatch and delivery in order. Customer explicitly activates only after recorded delivery and only while the replacement remains held. Activation changes the new instrument to active with channels still disabled; customer then uses its normal controls. Protective blocking of either instrument remains immediate, independent of checker authorization. A blocked new instrument cannot activate/resume; it may be the source of a later replacement. A delivery record is not courier proof. No PIN is requested or claimed to be set.

All mutations require a stable key, original role, displayed request/product version and a 5–300 character nonblank reason where appropriate. Issuance also binds the source version the approver reviewed; a concurrent protective block/control change produces a conflict and demands fresh review. Replay confirms the original command without another card/block/delivery/activation. Different payload/actor conflicts. Event, projection and audit failure rolls back the complete instruction. Unknown fields, cross-relationship products, stale versions and out-of-order actions fail server-side.

## HTTP, UI and recovery

Authenticated owned replacement list/detail/key enquiry and strict submit/action APIs follow existing deposits/service patterns. Customer/staff share request status, source/new card links and immutable event history. The Cards workspace can select original and issued replacement instruments; their control state/history and lifecycle links remain distinct. It never labels a request as an issued card before the persisted product exists.

Before a POST, store the full original input/key/role in relationship-scoped session storage. A lost/unverified response locks another instruction across reload and product/list failures. Inspect before retry/discard; only a confirmed missing key permits them, with the original actor/input. Storage failure blocks sending. Validate returned bank, source/request/card identities and confirmed key before success. Read-only refresh does not overwrite an unconfirmed command. Preview, draft, edit and navigation never POST.

## Verification and delivery

Pure domain states/validation live independently from clocks/storage/UI. Application commands use injected time and Store only. SQLite guards enforce owned source/current versions, one successor, independent issuance, delivery-before-activation, immutable histories and atomic source/new-card/audit effects. Existing card guards remain intact. Architecture fitness uses the existing dependency-cruiser/static gates; existing Effect/Schema/SQL/event patterns suffice.

Integration checks cover original and replacement controls, role/version/replay/ownership, races, terminal blocks, lost-card pre-block requirement, later-generation replacement and audit rollback at issuance/activation. Browser checks cover review/edit, independent staff steps, card selection, pending-list failure, storage failure, malformed/lost responses/reload, mobile/XL/200% text and no financial commands. Protected additive migration, full exact-source gate, private PR/main CI and live invented-data verification are required before closure. Wider issuance products, PIN, credit/prepaid/forex, real delivery and complete source parity remain open.
