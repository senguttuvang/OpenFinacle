# Savings-funded loan repayments

Execution: `of-9hc.15.12`; first typed boundary/proof child `.1`. This is an inferred OpenFinacle workflow over documented Fineract behaviour, not an observed proprietary customer/staff form. Source evidence was checked on 18 October 2026. No repayment is delivered by this contract alone.

## Core operation and correlation

Pinned [AccountTransfersWritePlatformServiceImpl](https://github.com/apache/fineract/blob/1.15.0/fineract-provider/src/main/java/org/apache/fineract/portfolio/account/service/AccountTransfersWritePlatformServiceImpl.java) executes savings withdrawal, loan repayment and linked transfer persistence inside one transaction for account types savings2 → loan1. Use this one supported operation. A loan cash repayment, two separate debit/credit POSTs, D1 allocation or a balance delta does not prove a savings-funded payment. No external settlement is involved.

The [transfer validator](https://github.com/apache/fineract/blob/1.15.0/fineract-provider/src/main/java/org/apache/fineract/portfolio/account/data/AccountTransfersDataValidator.java) accepts account/office/client IDs, date, amount and a required description of at most 200 characters. It does not accept a caller-supplied transaction external ID. The write service generates the loan transaction external ID itself. The [assembler](https://github.com/apache/fineract/blob/1.15.0/fineract-provider/src/main/java/org/apache/fineract/portfolio/account/domain/AccountTransferAssembler.java) preserves the original transfer description and both transaction links. Generate a unique immutable operation marker in that description and a separate original Core idempotency key; never use a customer-authored note as the marker.

Read-only recovery requires exactly one original marked loan repayment and savings withdrawal, both unreversed, owned, INR, exact amount/date and linked to the same transfer. The full transfer must independently corroborate its ID, marker, reversal state, both owned clients/offices, source savings, destination loan and types2 → 1. Loan allocation components must sum to the repayment; the source summary and schedule remain Core-owned. Missing, duplicate, reversed, malformed, foreign or contradictory evidence stays unresolved and never authorizes another POST.

The create acknowledgement's resource ID identifies transfer details, not necessarily the full transfer transaction. When an acknowledgement is available, verify the supported `accountDetailId` listing against the original corroborated transfer. The [read service](https://github.com/apache/fineract/blob/1.15.0/fineract-provider/src/main/java/org/apache/fineract/portfolio/account/service/AccountTransfersReadPlatformServiceImpl.java) filters that selector. Although the list API exposes `externalId`, the pinned read implementation does not apply it as a transfer-identity filter; do not infer absence or correlation from it. Embedded loan/savings transfer dates use their legacy arrays; the full transfer resource uses its strict ISO calendar date.

## First partial-payment policy

The first supported request is a current Indian banking-day partial repayment of ₹100 or more, exact to paise, strictly below the freshly verified principal outstanding and no more than available owned savings. Keep the supported product, ownership, active states, INR and no-transfer-fee configuration explicit. These are demonstration rules, not a bank quotation. Core determines allocation; no local principal/interest split, EMI or payoff engine is introduced.

A customer reviews an owned immutable offer, amount, funding account, current Core outstanding and expiry, then explicitly consents. The offer expires after fifteen minutes or Indian midnight, whichever comes first. Editing or stale financial conditions requires another offer/review. Officer assessment and independent approver authorization are separate saved decisions. Customer cancellation and staff rejection operate only before dispatch and while no original is unresolved. Quote expiry is not authority to clear a sent operation.

Full payoff, overpayment, early-settlement quotations, write-off, reversal, closed-state reconciliation and mandates remain unavailable until their own source-backed state/charge/consent contracts and real synthetic proofs are delivered. Do not allow an ostensibly partial amount to close the loan by accepting an amount at or above principal outstanding.

## Durable review and reservation boundary

Migration0014 adds `loan_repayment_offers`, `loan_repayment_requests`, `loan_repayment_operations` and `loan_repayment_events`. These record immutable observed offers, consent and decisions; they do not calculate a savings balance or loan ledger. Each offer binds the original owned active application, Core loan, original terms, savings owner, office, integer minor-unit amount and source observations. A customer can accept one unexpired current-day offer per pending loan repayment. Consent is immutable; cancelled/rejected requests remain history and cannot be reset or reuse the accepted offer.

The inferred OpenFinacle role sequence is customer submit → officer recommend → approver pay. Customer cancellation and the appropriate officer/approver rejection are separate decisions. Expired offers permit cancellation/rejection, never a new recommendation or dispatch. Every transition increments the request version and binds its original actor, command key and request. The synthetic persona roles demonstrate separation; they are not proof of distinct authenticated human identities.

The original approver operation atomically reserves the same `core_write_claims` account namespace used by savings commands and origination, appends its started event and marks savings/loan observations stale. The existing `owner_kind='loan'` namespace denotes lending; exactly one matching origination or repayment operation may own its UUID. SQL uniqueness arbitrates racing writers, including older Worker command SQL. An unacknowledged reservation cannot be dispatched by recovery. No claim expires or releases on missing Core proof. Only an executing operation may become a definite failure; uncertainty can only become positively confirmed.

Outcome persistence atomically updates original operation, claim/history, request/history/audit and the owned saved Core loan observation. Confirmation binds the original operation, amount, payment day, owned Core loan and unique unreversed marked repayment row/transfer with exact Core allocation. Adapter corroboration of both accounts and full transfer remains required before persisting this result. Observations refreshed while an operation remains executing/uncertain stay stale, including through older Worker paths. A failure to save any outcome/history part leaves the original reservation unresolved. A definite failure remains immutable; another attempt requires a fresh key/version/review of the still-valid unchanged offer.

`tests/loan-repayment-persistence.test.ts` rehearses the complete schema and populated native SQLite dump through strict `sqlite3 -bail` restore/integrity/FKs, role/owner/consent/time/version failures, cash race orders, immutable history and original evidence, stale refresh barriers and injected atomic failure.
