# Synthetic debit-card controls

This slice implements card enquiry, channel/limit changes, temporary hold/resume and permanent lost/stolen blocking. Card navigation and servicing families were observed; these specific forms, limits and staff permissions are inferred demonstration contracts. Full reference parity, card issuance/replacement, credit-card billing/payments and network integration remain open.

D1 owns explicitly synthetic debit-card records, separate from Fineract account balances and postings. Migration 0007 creates one synthetic card for each already-open relationship and database triggers create one when a relationship first opens. Reads never provision products. No PAN, CVV, PIN, OTP or real card credentials are collected. The displayed suffix is an invented demonstration label. Controls affect the simulated card record only; no actual card network is contacted.

Customers can update daily limits (whole rupees, 0–100000) and ATM, point-of-sale, online, contactless and international channel switches while active; hold an active card; resume a held card; or permanently block an active/held card with a reason. Officers can only permanently block with a reason; approvers have enquiry access. Immediate protective blocking does not wait for checker approval. Blocked cards are terminal. Holds retain saved channel settings but prevent simulated use. This slice supplies no purchase/ATM transaction or settlement simulation.

Authenticated GET /api/cards returns relationship-scoped records. GET /api/cards?id=... returns current state, ordered immutable history and role/state actions. POST /api/cards/action requires the displayed version, stable Idempotency-Key, action and reason. Settings actions require a complete settings object. Unknown/irrelevant fields fail validation. A command is an immutable event; a single insert and database trigger atomically update the product and audit. Version conflicts fail without overwriting another action. Reusing a key with different input fails; retrying the same input returns the saved event alongside current state. GET /api/cards?key=... reconciles interrupted commands. The browser retains pending input/key before sending and requires reconciliation after any unverified response, including reload.

Customer and staff screens share enquiry/history and expose only permitted actions. Changes use edit/review/confirm, no success before response validation, and explicit empty/loading/error/conflict states. Integration tests establish persisted effects, ownership, permissions, replay, races, atomic rollback and terminal guards. Browser tests establish review/edit, confirmation, history, recovery and role scope. Existing financial gates remain mandatory.
