# Approved synthetic customer maintenance

Address, email, home-branch and employer maintenance use the existing independently authorized service-case lifecycle. On approver fulfilment, the selected fields actually change the persistent synthetic relationship profile. Customer and staff enquiry share that profile and immutable snapshots with source-case references. No Fineract client, account, identity master, balance or posting changes. Mobile/name remain enquiry-only. Forms and branch permission policy remain inferred demonstration contracts.

Migration 0008 imports the current application-supplied contact/employment data or the existing invented demo baseline for opened relationships. Its initial event states that earlier maintenance effects are unavailable. Previously completed cases remain historical records; their effects are not retroactively invented. New relationships receive their baseline once when their account first opens, never on enquiry. Existing profiles are not reset by visits, role switches or repeated account updates.

An approver fulfilment of one of the four supported case codes records a domain-selected profile patch, inserts an immutable profile snapshot and updates matching fields in the same SQLite statement as case history/audit. Other fields are retained. Processing, requesting/providing information, rejection, cancellation, delivery and repeated/stale completion do not apply profile changes. The latest successful approval of a field becomes current; original case input and every earlier profile snapshot remain available. A failure applying any effect rolls back the case, profile, history and audit together. After migration, an older Worker lacking the domain patch cannot silently complete these four kinds; preserve the additive schema and deploy a forward fix rather than bypassing this guard.

Authenticated GET /api/profile returns the relationship-scoped current profile and ordered snapshots. There is no profile-writing route; all changes go through customer submission, officer processing and independent approval. Customer/staff screens display imported versus approved-change history and navigate to source cases. Read/command paths never call core. Validation, ownership, concurrent case fulfilment, field preservation, atomic failures and browser reload/role consistency are acceptance evidence. The full exact-source delivery gate and protected migration release procedure remain mandatory.
